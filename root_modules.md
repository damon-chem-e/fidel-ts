# Root Modules Documentation

This document describes all modules currently located in the repository root directory and provides a plan for restructuring the codebase into a clean, modular Typer CLI architecture.

## Current Root-Level Modules

### Training/Execution Scripts

#### `run.py`
- **Purpose**: Main entry point for PyTorch-based training pipeline
- **Description**: Traditional PyTorch training script with manual training loop implementation. Supports various time series forecasting models (DLinear, FITS, PatchTST, TGTSF, iTransformer, etc.). Handles argument parsing, configuration loading (model and data YAML files), device management, and experiment execution via `exp.exp_universal.Experiment`.
- **Key Features**: 
  - Supports single and multi-GPU training
  - Configurable ahead tasks (day/week/month forecasting)
  - Early stopping with patience
  - Learning rate scheduling
  - Checkpoint management
- **Dependencies**: `exp.exp_universal`, `utils.tools`, `utils.task`

#### `run_lightning.py`
- **Purpose**: Main entry point for PyTorch Lightning-based training pipeline
- **Description**: Similar to `run.py` but uses PyTorch Lightning framework for more structured training, better multi-GPU support, and experiment tracking. Calls `exp.exp_lightning.train_lightning_model` for training execution.
- **Key Features**:
  - Multi-GPU training with DDP
  - Precision control (32/16/bf16)
  - Gradient clipping
  - TensorBoard logging
  - Test after epoch option
- **Dependencies**: `exp.exp_lightning`, `utils.tools`, `utils.task`

#### `run_llm.py`
- **Purpose**: Entry point for LLM-based time series forecasting experiments
- **Description**: Specialized script for running Large Language Model (LLM) reasoning-based forecasting tasks. Uses `exp.exp_llm.Experiment` for execution. Supports models like DeepSeek-R1 and other LLM-based forecasting approaches.
- **Key Features**:
  - LLM model configuration
  - Parallel processing control
  - Validation set specification
  - Filtered sample support
- **Dependencies**: `exp.exp_llm`, `utils.tools`, `utils.task`

#### `run_fm.py`
- **Purpose**: Entry point for Foundation Model (FM) testing
- **Description**: Script for testing foundation models like Chronos. Uses `exp.exp_fm.Experiment` for execution. Supports both TSF and TGTSF tasks, with individual channel training options.
- **Key Features**:
  - Foundation model testing
  - Individual channel model support
  - Filtered sample testing
- **Dependencies**: `exp.exp_fm`, `utils.tools`, `utils.task`

### Visualization Scripts

#### `visualize.py`
- **Purpose**: Visualization tool for TSF/TGTSF model predictions
- **Description**: Creates prediction plots comparing input history, ground truth, and model predictions. Loads checkpoints, runs inference on test samples, and generates matplotlib visualizations saved as PNG files.
- **Key Features**:
  - Single sample visualization
  - Channel-specific or all-channel plotting
  - Timestamp-based x-axis formatting
  - Configurable output paths
- **Dependencies**: `models`, `data_provider.data_factory`, `utils.tools`

#### `visualize_llm.py`
- **Purpose**: Visualization tool for LLM-based forecasting results
- **Description**: Similar to `visualize.py` but reads prediction results from JSON files generated by LLM experiments. Visualizes predictions stored in checkpoint directories with date-based sample identification.
- **Key Features**:
  - JSON-based result loading
  - Date-based sample identification
  - Ground truth vs prediction comparison
- **Dependencies**: Standard plotting libraries (matplotlib, pandas, numpy)

#### `visualize_lightning.py`
- **Purpose**: Visualization tool for Lightning-trained models
- **Description**: Visualization script specifically designed for models trained with PyTorch Lightning. Supports both TSF and TGTSF tasks, with flexible checkpoint selection (best/last).
- **Key Features**:
  - Lightning checkpoint compatibility
  - Subset and sample ID specification
  - Flexible checkpoint file selection
- **Dependencies**: `models`, `data_provider.data_factory`, `utils.tools`

### Evaluation/Criteria Scripts

#### `criterias.py`
- **Purpose**: Evaluation script for time series forecasting models
- **Description**: Comprehensive evaluation tool that tests trained models on test datasets. Supports channel-wise evaluation, filtered sample testing, and provides detailed metrics (MSE, MAE) per dataset subset.
- **Key Features**:
  - Full dataset evaluation
  - Channel-wise metrics
  - Filtered sample support
  - Multiple task support (TSF, TGTSF, MTSF)
- **Dependencies**: `models`, `data_provider.data_factory`, `utils.tools`, `utils.metrics`

#### `criterias_lightning.py`
- **Purpose**: Evaluation script for Lightning-trained models
- **Description**: Similar to `criterias.py` but specifically designed for models trained with PyTorch Lightning. Handles Lightning checkpoint format and state dict loading.
- **Key Features**:
  - Lightning checkpoint compatibility
  - Channel-wise evaluation
  - Filtered sample testing
- **Dependencies**: `models`, `data_provider.data_factory`, `utils.tools`

#### `criterias_llm_all_sample.py`
- **Purpose**: Evaluation script for LLM-based forecasting across all samples
- **Description**: Evaluates LLM predictions from JSON files across all samples in a checkpoint directory. Calculates standardized MAE and MSE metrics, supports multivariate data, and can include/exclude LLM failure cases.
- **Key Features**:
  - Batch evaluation of JSON prediction files
  - Standardization using dataset statistics
  - Anomaly detection reporting
  - Weighted average metrics
  - LLM failure handling
- **Dependencies**: Standard libraries (numpy, json, pandas)

### Filtering Scripts

#### `filter.py`
- **Purpose**: Sample filtering for reasoning-based training
- **Description**: Filters training samples by comparing TST (Time Series Transformer) and TGTSF model performance. Identifies samples where TGTSF significantly outperforms TST (positive samples) or underperforms (negative samples) for use in LLM reasoning training.
- **Key Features**:
  - Loss-based sample selection
  - Weighted sampling (positive/negative)
  - CSV loss dataframe generation
  - JSON sample index output
- **Dependencies**: `models`, `data_provider.data_factory`, `utils.tools`, pandas
- **Downstream Usage**: The filtered samples (stored as JSON files in `sample_indexes/`) are extensively used in:
  - **LLM training/testing** (`run_llm.py`, `exp/exp_llm.py`): Used to select which samples to run LLM reasoning on, focusing on cases where text guidance significantly helps or hurts performance
  - **Foundation model testing** (`run_fm.py`, `exp/exp_fm.py`): Used to test foundation models on specific filtered sample sets
  - **Model evaluation** (`criterias.py`, `criterias_lightning.py`): Used to evaluate models only on filtered samples for comparative analysis
  - **Comparative model testing**: Many shell scripts test various models (DLinear, PatchTST, TGTSF, Chronos, etc.) on filtered sample sets to compare performance on cases where text guidance is most impactful

#### `filter_without_inference.py`
- **Purpose**: Sample filtering using pre-computed loss dataframes
- **Description**: Similar to `filter.py` but reads pre-computed loss dataframes from CSV files instead of running inference. More efficient for re-filtering with different sampling rates.
- **Key Features**:
  - CSV-based loss loading
  - Re-filtering with different rates
  - No model inference required
- **Dependencies**: pandas, json
- **Downstream Usage**: Same as `filter.py` - generates the same JSON sample index files used throughout the pipeline

## Planning: Typer CLI Restructure

### Target Architecture

The goal is to restructure the codebase into a clean, modular Typer CLI structure with the following organization:

```
.
├── cli/                    # CLI module package
│   ├── __init__.py
│   ├── train.py           # Training command: python -m cli.train config.yaml
│   ├── test.py             # Testing command: python -m cli.test config.yaml
│   ├── visualize.py       # Visualization command: python -m cli.visualize config.yaml
│   ├── filter.py          # Filtering command: python -m cli.filter config.yaml
│   └── config/            # Configuration handling
│       ├── __init__.py
│       ├── loader.py      # Config loading and validation
│       └── schema.py      # Config schemas
├── runs/                  # Run modules (experiment execution)
│   ├── __init__.py
│   ├── pytorch.py         # PyTorch training runs
│   ├── lightning.py       # Lightning training runs
│   ├── llm.py             # LLM experiment runs
│   └── fm.py              # Foundation model runs
├── visualization/         # Visualization module
│   ├── __init__.py
│   ├── tsf.py             # TSF/TGTSF visualization
│   ├── llm.py             # LLM visualization
│   └── lightning.py       # Lightning visualization
├── evaluation/            # Evaluation/criteria module
│   ├── __init__.py
│   ├── standard.py        # Standard evaluation
│   ├── lightning.py       # Lightning evaluation
│   └── llm.py             # LLM evaluation
├── filtering/             # Filtering module
│   ├── __init__.py
│   ├── reasoning.py       # Reasoning sample filtering
│   └── utils.py           # Filtering utilities
├── configs/               # Configuration files (existing)
│   ├── data_configs/

├── README.md              # Main README (links to docs/)
├── requirements.txt
├── .gitignore
└── pyproject.toml         # Package configuration (optional)
```

### CLI Structure Design

#### Training Command (`cli/train.py`)

```python
# Example structure
import typer
from cli.config.loader import load_config
from runs import pytorch, lightning, llm, fm

app = typer.Typer()

@app.command()
def pytorch(config_path: str):
    """Train using PyTorch pipeline"""
    config = load_config(config_path)
    pytorch.run(config)

@app.command()
def lightning(config_path: str):
    """Train using PyTorch Lightning pipeline"""
    config = load_config(config_path)
    lightning.run(config)

@app.command()
def llm(config_path: str):
    """Train/test using LLM pipeline"""
    config = load_config(config_path)
    llm.run(config)

@app.command()
def fm(config_path: str):
    """Test foundation models"""
    config = load_config(config_path)
    fm.run(config)

if __name__ == "__main__":
    app()
```

Usage: `python -m cli.train pytorch config.yaml` or `python -m cli.train lightning config.yaml`

### Migration Plan

#### Phase 1: Create New Structure
1. Create new directory structure (`cli/`, `runs/`, `visualization/`, `evaluation/`, `filtering/`)
2. Create `cli/train.py`, `cli/test.py`, `cli/visualize.py`, `cli/filter.py` with basic Typer app structure
3. Create configuration loader with subconfig support in `cli/config/`
4. Create placeholder modules in `runs/`, `visualization/`, `evaluation/`, `filtering/`

#### Phase 2: Migrate Run Scripts
1. Move `run.py` logic to `runs/pytorch.py`
2. Move `run_lightning.py` logic to `runs/lightning.py`
3. Move `run_llm.py` logic to `runs/llm.py`
4. Move `run_fm.py` logic to `runs/fm.py`
5. Update `cli/train.py` with subcommands (pytorch, lightning, llm, fm)

#### Phase 3: Migrate Visualization Scripts
1. Move `visualize.py` logic to `visualization/tsf.py`
2. Move `visualize_llm.py` logic to `visualization/llm.py`
3. Move `visualize_lightning.py` logic to `visualization/lightning.py`
4. Update `cli/visualize.py` with subcommands (tsf, llm, lightning)

#### Phase 4: Migrate Evaluation Scripts
1. Move `criterias.py` logic to `evaluation/standard.py`
2. Move `criterias_lightning.py` logic to `evaluation/lightning.py`
3. Move `criterias_llm_all_sample.py` logic to `evaluation/llm.py`
4. Update `cli/test.py` with subcommands (standard, lightning, llm)

#### Phase 5: Migrate Filtering Scripts
1. Move `filter.py` logic to `filtering/reasoning.py`
2. Move `filter_without_inference.py` logic to `filtering/reasoning.py` (as alternative function or merge)
3. Update `cli/filter.py` with subcommands (reasoning, from_csv)

#### Phase 6: Cleanup and Documentation
1. Remove old root-level scripts (or keep as deprecated wrappers)
2. Update README.md with new CLI usage
3. Create documentation in `docs/` folder
4. Update all import paths throughout codebase
5. Test all commands with example configs

### Configuration Management

The configuration system should support:
- **Primary config files**: Main experiment configuration
- **Subconfigs**: Referenced configs for specific components (plotting, evaluation, etc.)
- **Validation**: Schema validation using Pydantic or similar
- **Defaults**: Sensible defaults with override capability
- **Environment variables**: Support for environment-based overrides

### Benefits of This Structure

1. **Clean Root**: Only essential files (README, requirements.txt, .gitignore, cli module) at root
2. **Modularity**: Clear separation of concerns (runs, visualization, evaluation, filtering)
3. **Extensibility**: Easy to add new commands or subcommands
4. **Configuration**: Centralized config management with subconfig support
5. **Type Safety**: Typer provides automatic CLI validation and help generation
6. **Documentation**: Clear structure makes it easier to document and maintain
7. **Testing**: Modular structure facilitates unit testing

### Notes

- The existing `exp/`, `models/`, `data_provider/`, `utils/`, `layers/` directories should remain as-is since they contain core functionality
- Configuration files in `data_configs/` and `model_configs/` should remain in their current locations
- The `scripts/` directory can remain for backward compatibility or be migrated to use the new CLI
- Consider adding a `pyproject.toml` for proper package configuration and CLI entry points
- **Filter Module Importance**: The filtering modules are critical to the workflow - they generate JSON sample index files (`sample_indexes/*.json`) that are used extensively downstream for:
  - LLM reasoning training/testing (focusing on samples where text guidance is most impactful)
  - Comparative model evaluation (testing various models on the same filtered sample sets)
  - Foundation model testing on specific interesting samples
  - The filtered samples help identify cases where TGTSF significantly outperforms or underperforms compared to TST, which is valuable for understanding when text guidance is beneficial
